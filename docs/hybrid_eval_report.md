# Hybrid Chat Evaluation Report (M4)

> **Historical report (kept as assessment evidence).** M4 run of 23 Nov 2026 with the earlier temporary Groq LLM; the same evaluation with Azure OpenAI GPT-4.1 is in [azure_eval_report.md](azure_eval_report.md). Current results: [README - Testing](../README.md#testing), [azure_eval_report.md](azure_eval_report.md) (GPT-4.1, 24 Nov 2026) and the Azure production verification (17/17, 25 Nov 2026) in [project_plan.md](project_plan.md).

Date: 2026-11-23 | Commit: `7e2e866` (plus uncommitted changes) | Python 3.14.8 on Windows

Environment: HTTP against an isolated backend (http://127.0.0.1:8301) | LLM: `qwen/qwen3.8-27b` via Groq (temporary)

Dataset: `tests/eval/heldout_questions.json` - 62 held-out questions, session employee EMP001. Generated by `python -m scripts.hybrid_eval`. Expectations for records come from the database at run time; handbook answer keys are verbatim knowledge-base text.

> **Run context (M4).** End-to-end run through `tests/load/run_isolated_load_test.sh` (`WITH_EVAL=1`, `INDEX_SRC` = a
> freshly built PDF index): backend image built from the working tree, temporary PostgreSQL 16 seeded only from
> `docker/postgres`, backend as `onboardai_app` + `onboardai_reader` with the signed employee scope, PDF index
> (handbook.pdf canonical + faqs.md, small-to-big windows) mounted read-only, Groq for handbook answers. The live
> Docker stack, its data and `data/index` were not used. The held-out dataset is unchanged since M3
> (`git diff` empty). Reproduced in-process (isolated SQLite copy, same index and model): every quality metric
> identical; in-process latency p50/p95 ms - records 117/225, handbook 345/3500, mixed 327/2472.

## Method and limitations

- The held-out set was written before measurement and was not used to change the router; misses are reported, not fixed, in M3.
- Grading is lexical: an answer key must appear verbatim (case-insensitive). Paraphrased correct answers can be counted as not grounded; unsupported paraphrased claims are not detected.
- Records correctness requires every expected value (for example all leave types) to appear in the records part.
- Leak detection checks other employees' names, emails and asset names from the synthetic seed; it cannot prove the absence of every possible leak (database RLS is the primary control and is tested separately).
- One run, one model, temperature 0; LLM answers can still vary between runs. Transient LLM errors are retried up to twice and reported.
- In-process latency excludes HTTP, nginx and PostgreSQL; use --base-url against an isolated stack for end-to-end latency.
